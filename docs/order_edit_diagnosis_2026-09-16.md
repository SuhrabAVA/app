# Диагностика проекта и блокировка редактирования заказов

Дата: 16.09.2026. Рабочий проект: `C:/dev/easy_pack_pro`.

## Результат и статус внедрения

Миграция `supabase/migrations/20260916064742_order_edit_leases.sql` **применена
к рабочей базе 16.09.2026** под именем `order_edit_leases`. Перед применением
из неё убран триггер `orders_edit_full_guard` — см. «Отличие от первой
редакции». Осталось пересобрать и разослать приложение.

До того как приложение обновят, клиент работает в режиме совместимости: если
серверных функций нет или нет входа в Supabase, заказ открывается как раньше, а
над формой висит закрываемое предупреждение. Ни создание, ни сохранение заказа
при этом не падают.

### Отличие от первой редакции миграции

Первая редакция добавляла второй триггер `orders_edit_full_guard`
(`before update of manager`, `check_write(..., p_require => true)`). Он требовал
ключ редактора при каждом полном сохранении заказа — в том числе когда
блокировку уже освободили. Поскольку `release` не удаляет строку, а ставит
`expires_at = '-infinity'`, у любого заказа, однажды открытого новой сборкой,
навсегда оставалась строка блокировки, и устройства со старой сборкой теряли
возможность сохранить этот заказ. Обновлять все планшеты и компьютеры
одновременно нечем, поэтому триггер убран.

Итог: блокировка действует ровно пока заказ держат открытым (90 секунд с
продлением каждые 20). После сохранения и выхода заказ снова доступен всем,
включая необновлённые устройства. Это то поведение, которое и требовалось:
второй сотрудник ждёт, пока первый сохранит.

## Причина потери изменений

1. `EditOrderScreen` получал снимок заказа из списка. Два сотрудника могли открыть
   один снимок независимо друг от друга.
2. `OrdersProvider.updateOrder` отправлял полный `toMap(includeNulls: true)` по ID,
   без блокировки или проверки версии. Последняя запись затирала предыдущую.
3. Экран закрывался до выполнения сетевой части сохранения. Запись заказа,
   очереди, красок, файлов и формы продолжалась в фоне.
4. `updateOrder` перехватывал ошибку, откатывал локальный список и не передавал
   исключение вызывающему коду. Последующие этапы могли выглядеть успешными.
5. Все устройства используют общую Supabase-учётную запись. Одного `auth.uid()`
   недостаточно для различения редакторов.

## Что изменено

- Каждый открытый редактор получает отдельный случайный UUID-ключ. Серверная
  операция захвата атомарна: при одновременном открытии победитель один.
- До получения блокировки форма не создаётся. После захвата заказ перечитывается
  из БД, поэтому следующий сотрудник получает сохранённые изменения предыдущего.
- Секретные ключи хранятся в закрытой схеме с RLS без прямого клиентского доступа.
  Публичная функция списка возвращает только ID заказа и имя редактора.
- Карточка и строка таблицы получают синюю пульсирующую рамку; кнопка
  редактирования блокируется, подсказка показывает сотрудника. Проверка списка
  раз в 2 секунды; запоздавший индикатор не отменяет серверную проверку.
- Режим уменьшения анимаций сохраняет синюю рамку без пульсации.
- Блокировка действует 90 секунд и продлевается каждые 20 секунд. Выход из
  редактора освобождает её; аварийное закрытие освобождает по истечении срока.
  При потере связи форма блокируется до подтверждения владения. После истечения
  срока редактор не захватывает заказ повторно поверх чужих изменений.
- Секрет передаётся HTTP-клиентом только в REST-запросах к своему Supabase-хосту.
  Триггеры проверяют основную запись, краски, файлы и структуру очереди.
- Сохранение удерживает экран и блокировку до завершения операций. Ошибки
  основной записи и загрузки/связи PDF больше не маскируются успехом. При ошибке
  можно повторить сохранение; уже созданный заказ не вставляется повторно.
- Производственные показатели и сведения об отгрузке исключены из полного
  обновления формы, чтобы открытый редактор не возвращал их старые значения.
  Завершённый производством статус не откатывается сохранением старого снимка.
- Выполнение этапа, его фактические показатели и комментарии не требуют захвата
  редактора; изменение структуры маршрута защищено блокировкой.

### Проверка на рабочей схеме перед применением (16.09.2026)

Миграция дважды прогонялась холостым ходом на самой рабочей базе: вся пачка в
одной транзакции, в конце `raise` — всё откатывалось. Второй прогон подставлял
`request.jwt.claims`, иначе `auth.uid()` пуст и `check_write` молча пропускает
любую запись, то есть проверка ничего не доказывает. При активной чужой
блокировке на реальном заказе:

| Действие | Ожидание | Результат |
|---|---|---|
| `orders.actual_qty` (цех) | проходит | проходит |
| `orders.customer` (второй менеджер) | `55P03` | `55P03` |
| `delete from order_paints` (второй менеджер) | `55P03` | `55P03` |
| `orders.customer` после `release` | проходит | проходит |

Отдельно сверено, что `advance_order_after_task_completion` — функция, которую
вызывает цех при завершении задачи, — пишет в `prod_plan_stages` только
`status/finished_at/completed_at`, а в `orders` только `status`. Ни те, ни другие
колонки под триггеры не попадают, поэтому завершение этапа не встаёт из-за
открытой у менеджера формы.

## Внедрение и ограничения

1. Миграция применена 16.09.2026 (см. «Результат и статус внедрения»).
2. Пересобрать и разослать приложение. Одновременное обновление всех устройств
   не требуется: старая сборка не знает протокол блокировки, но её запись
   отклоняется только пока заказ действительно держат открытым в новой сборке.
   Пока в конторе есть старые сборки, одновременное редактирование защищено
   лишь наполовину — старая сборка не показывает синюю рамку и даст открыть
   форму, хотя сохранить не позволит.
3. Проверить на двух устройствах: А открывает → Б видит синюю рамку и не может
   редактировать → А сохраняет → Б открывает свежие данные. Повторить с потерей сети.
4. Проверить в цехе: завершение этапа и ввод количества по заказу, который в
   этот момент открыт у менеджера, должны проходить.

Блокировка предотвращает одновременную запись редакторов, но вся существующая
процедура сохранения ещё состоит из нескольких HTTP-запросов, а не одной SQL-
транзакции. При ошибке позднего шага ранние шаги могут быть уже записаны; форма
остаётся открытой для завершения. Файлы в Storage также не участвуют в SQL-
транзакции. Новая блокировка — защита от конфликтов, не индивидуальная система
авторизации сотрудников: для неё потребуются отдельные Supabase-пользователи.
